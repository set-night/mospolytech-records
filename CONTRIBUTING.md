# Как помочь проекту

Спасибо, что заглянули! Любая помощь ценна: сообщение об ошибке, идея, правка текста или код.

## Сообщить об ошибке или предложить идею

Откройте [issue](https://github.com/set-night/mospolytech-records/issues/new/choose) и выберите шаблон.
Для ошибок укажите версию приложения (раздел «О программе»), систему и группу.

## Подготовка

Нужны Node.js 24 (см. `.nvmrc`) и git.

```bash
git clone https://github.com/set-night/mospolytech-records.git
cd mospolytech-records
npm install
npm run dev
```

| Команда | Что делает |
|---|---|
| `npm run dev` | приложение с горячей перезагрузкой |
| `npm run check` | ESLint, проверка типов и тесты — то же, что в CI |
| `npm run pack` | собрать распакованное приложение в `dist/` |
| `npm run dist` | установщики для текущей ОС |

## Устройство проекта

Код разложен по фичам, а не по слоям:

```
src/
  shared/              типы и схемы zod, общие для всех процессов
  main/                процесс Electron
    index.ts           точка сборки: создаёт части и связывает их
    schedule/          загрузка и кэш расписания rasp.dmami.ru
    recorder/          план записи, вход в вебинар, MediaRecorder, реакции на статус
    recordings/        записи на диске и место под них
    settings/          настройки
    updates/           поиск, загрузка и установка новых версий
      release.ts       релизы GitHub: версия, список изменений, установщик под сборку
      policy.ts        чистые решения: какая сборка, можно ли ставить сейчас
      updater.ts       состояние обновления поверх electron-updater
      reactions.ts     уведомления, трей и тихая установка
    net.ts             JSON по HTTP с таймаутом, лимитом и повторами
    window.ts, notifier.ts, tray.ts, ipc.ts, autostart.ts
  preload/             безопасный мост window.api
  renderer/src/
    features/          экраны: status, schedule, recordings, settings, onboarding, about
    shared/            общие компоненты и хуки
tests/                 тесты vitest
```

Правила, которых мы держимся:

- **TypeScript без `any`.** Данные извне (расписание, IPC, файлы настроек) проверяются схемами zod на границе — дальше коду можно доверять.
- **Тесты на реальных данных, а не на моках.** Файловая система — во временной папке, расписание — на сохранённых
  ответах rasp.dmami.ru, сеть — на локальном HTTP-сервере (`tests/http.ts`).
- **Решения отдельно от Electron.** Логику вроде «можно ли сейчас ставить обновление» держим в чистых функциях,
  чтобы её можно было проверить тестом без запуска приложения.
- **Интерфейс — на русском**, коротко и понятно человеку, который не разбирается в технике.

## Коммиты и pull request

- Сообщения коммитов и заголовок PR — в формате [Conventional Commits](https://www.conventionalcommits.org/ru/):
  `feat(schedule): показывать номер аудитории`, `fix(recorder): …`. Типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`.
- Перед PR запустите `npm run check`.
- PR сливаются через squash — один PR, один коммит в `main`, поэтому заголовок PR важнее отдельных коммитов.
- Если меняется интерфейс — приложите скриншот.

### Заголовок PR — это текст для пользователей

Заголовки `feat`, `fix` и `perf` попадают в описание релиза и в карточку «Что нового» в самом приложении.
Пишите их **по-русски и словами пользователя**: что стало лучше для него, а не что поменялось в коде.

| Так | Не так |
|---|---|
| `feat(updates): обновляется сам, когда приложение свёрнуто` | `feat(updates): add Updater class with canInstallNow policy` |
| `fix(recorder): запись не обрывается при смене сети` | `fix(recorder): handle ECONNRESET in session` |

Остальные типы (`refactor`, `docs`, `ci`, …) в список изменений не попадают, их можно писать как удобно.

Если в одном PR несколько заметных изменений, перечислите их в описании PR — каждое станет отдельным пунктом:

```
BEGIN_COMMIT_OVERRIDE
feat(updates): обновляется сам, когда приложение свёрнуто и пар нет
feat(about): кнопка «Проверить» и время последней проверки
fix(settings): повреждённый файл настроек сохраняется в копию
END_COMMIT_OVERRIDE
```

Блок читает release-please, когда собирает следующий релиз. Править его можно и после слияния — до выпуска версии.

## Выпуск версии

Версии выходят сами — руками ничего поднимать не нужно.

1. Каждый `feat:`, `fix:` или `perf:` в `main` обновляет PR **chore(release): vX.Y.Z**: в нём новая версия
   в `package.json` и `CHANGELOG.md`, собранный из заголовков коммитов. `feat` поднимает минорную версию,
   `fix` и `perf` — патч, `feat!` или `BREAKING CHANGE:` — мажорную.
2. Когда готовы выпускать, слейте этот PR. Появится тег и релиз, а workflow **Release** соберёт установщики
   на Windows, macOS и Linux и прикрепит их вместе с файлами для автообновления и `SHA256SUMS.txt`.
   Описание релиза собирается само: что нового → таблица «Скачать» → «Как обновиться» → контрольные суммы
   (шаблон — `.github/release-notes.md`).
3. Установленные приложения найдут новую версию. `.exe` и AppImage скачают её в фоне и поставят, когда
   окно свёрнуто и пар нет; `.msi`, `.deb` и macOS пришлют уведомление с прямой ссылкой на установщик.

Проверить настоящий цикл обновления можно только на выпущенной версии: поставьте предыдущий релиз,
выпустите новый и посмотрите «О программе» и `app.log`. Логику выбора момента покрывают тесты в `tests/updates.test.ts`.

> PR, созданный ботом Actions, не запускает CI сам. Чтобы проверки прошли, закройте и откройте его
> заново или добавьте в него пустой коммит.

Тег вида `v0.2.0`, отправленный вручную, тоже запускает **Release** — на случай, если нужно пересобрать.
